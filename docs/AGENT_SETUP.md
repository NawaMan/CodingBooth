# CodingBooth Guide for AI Agents — Outside the Booth

**Purpose:** Help an AI agent working on the **host** — setting up a booth for a user's project, or
driving one that already exists.

---

## Am I in the Right Place?

```bash
[[ -f /opt/codingbooth/version.txt ]] && echo "INSIDE" || echo "OUTSIDE"
```

**INSIDE a booth:** stop and read `/opt/codingbooth/AGENT.md` instead.

**OUTSIDE:** check which situation you are in:

```bash
ls -a .booth/ 2>/dev/null       # is there a booth?
head -2 .booth/Boothfile        # "# Configured by: booth config ..." → generated by booth config
ls .booth/.generated            # present → booth config is tracking these files
```

| Situation | Read |
|---|---|
| No `.booth/` — the user wants one | [Set up a booth](#set-up-a-booth) |
| `.booth/` exists — the user wants it changed | [Change an existing booth](#change-an-existing-booth) |
| `.booth/` exists — you need to build, test or run the project | [Drive an existing booth](#drive-an-existing-booth) |

For the human-facing versions of the same material, point the user to
[Setting Up a Booth](https://github.com/NawaMan/CodingBooth/blob/main/docs/SETUP_GUIDE.md) and
[Developing in a Booth](https://github.com/NawaMan/CodingBooth/blob/main/docs/USER_GUIDE.md).

---

## The Rule That Matters Most

**Never write `.booth/Boothfile` or `.booth/config.toml` by hand.** They are generated by
`booth config`, which records a fingerprint of them in `.booth/.generated`. A file it did not
write, or an edit it cannot turn back into flags, is treated as hand-written from then on:
`booth config --no-tui` refuses to run without `--overwrite` or `--beside`, and the config TUI
opens behind a warning dialog. That is an expensive way to lose the user's tooling.

Everything you want to put in those files has a `booth config` flag. Find it with
`booth config --help` rather than reaching for an editor.

The rest of `.booth/` — `setups/`, `startups/`, `home/`, `home-seed/`, `shared/`, `console.json`,
`templates/` — is copied, not regenerated, so writing those by hand is fine.

---

## Prerequisites

```bash
docker info            # must work WITHOUT sudo
```

- **Linux:** rootful Docker Engine, user in the `docker` group
  (`sudo usermod -aG docker $USER`, then log out and back in). **Rootless Docker and userns-remap
  are not supported**; `booth` refuses to start on them.
- **macOS / Windows:** Docker Desktop.
- Podman and Apple container are experimental alternatives.

If Docker is missing or down, stop and tell the user. Don't work around it on the host.

## Set Up a Booth

### 1. Install CodingBooth in the project

```bash
curl -fsSL https://codingbooth.io/install.sh | bash   # if `booth` is not installed yet
cd <project>
booth install -y                                      # puts ./booth and .booth/tools/codingbooth.lock here
```

### 2. Look at what the project needs

Read the project's own files before choosing anything:

| File | Template |
|---|---|
| `go.mod` | `go` (`+go-mod` to pre-fetch modules) |
| `package.json` | `nodejs` (`+npm-install`, `+pnpm-install` or `+yarn-install` to match the lock file) |
| `pyproject.toml`, `requirements.txt` | `python` (`+uv` or `+pip`) |
| `pom.xml` | `java+maven` |
| `build.gradle(.kts)` | `java+gradle` |
| `Cargo.toml` | `rust` |
| `Gemfile` | `ruby+bundle-install` |
| `composer.json` | `php+composer` |
| `mix.exs` | `elixir+mix-deps` |
| `*.csproj`, `*.sln` | `csharp` or `dotnet` |
| `docker-compose.yml` | `docker-compose`, and possibly `dind` (privileged — see step 5) |
| A database the app talks to | `postgresql`, `mysql`, `redis`, `mongodb`, … |

Pin the version the project already declares (`.nvmrc`, `go 1.25` in `go.mod`,
`<java.version>`): `nodejs:22`, `java:21`. Leave out a pin that equals the template default;
it adds noise and nothing else.

Then confirm the names and what each template offers:

```bash
booth template search <keyword>
booth template show <name>              # params, extensions, requirements
```

### 3. Ask the user what you can't read from the files

- **How do they want to open it?** `base` (browser terminal), `codeserver` (VS Code), `notebook`
  (Jupyter), or a desktop (`xfce`, `kde`). Pass it with `--variant`.
- **Which credentials does the booth need?** Use the templates — `git-credential`, `ssh`,
  `gh+credential`, `<ai-tool>+credential` — never hand-written `-v` mounts. Bring in only what the
  project needs.
- **Which AI tools do they use in the booth?** For example `claude-code+credential+auto-accept`.

### 4. Preview, then write

```bash
booth config --no-tui --dryrun --variant codeserver \
    --select 'go+linter/postgresql/git-credential/claude-code+credential' \
    --expose '+80:8080'
```

Show the user the dryrun output. When they agree, run the same command **from inside the project
folder** without `--dryrun`. Passing the path as an argument instead puts that absolute path into
the committed header.

Ports, env vars, mounts and other settings are flags on the same command: `--expose`, `--env`,
`--mount`, `--cmd`, `--port`, and `--set <key>=<value>` for any other `config.toml` key.

### 5. Ask before anything privileged

`dind`, `--privileged`, extra capabilities, engine socket mounts and host devices let code inside
the booth reach the host. `booth` asks the user before starting such a booth. Explain the trade-off
**before** you add one; don't just let the user find the prompt.

### 6. Prove it works

```bash
./booth -- go version                   # or whatever the toolchain is
./booth -- just test                    # if the project has a Justfile
```

Then check the round trip, so the next `booth config` reproduces exactly these files:

```bash
git add .booth && booth config --no-tui --overwrite && git diff --exit-code .booth
```

"It generated" is not "it works". Run the compiler, run the tests, check the credential.

### 7. Tell the user what to commit

- `./booth`, `.booth/tools/codingbooth.lock`
- `.booth/Boothfile`, `.booth/config.toml`, **`.booth/.generated`** — without the fingerprint file,
  hand-edits go undetected after a clone
- anything under `.booth/setups/`, `startups/`, `home/`, `home-seed/`, `shared/`

The generated `.booth/.gitignore` keeps out `.env`, `.<profile>--env`, `cache/`, `.tmp/` and the
rest. Commit only
when the user asks.

## Change an Existing Booth

Line 2 of the Boothfile records the command that produced it. A new `booth config` run starts from
that baseline, so pass only the change:

```bash
booth config --no-tui --overwrite --add-select docker           # add a template
booth config --no-tui --overwrite --add-select go+vscode-ext    # add an extension to an existing template
booth config --no-tui --overwrite --remove-select python        # drop one
booth config --no-tui --overwrite --add-env TZ=UTC              # also --add-expose, --add-mount, --remove-*
```

A setting you leave out keeps its recorded value. **Restating a list flag (`--select`, `--env`,
`--expose`, `--mount`) replaces the whole list.** That's how a toolchain silently disappears, so
prefer the `--add-*` / `--remove-*` forms.

### A tool that has no template

| Need | Do |
|---|---|
| A system package | `--add-select 'apt-pkg:htop,jq'` |
| A language package | the language's `*-pkg` extension, e.g. `--add-select 'nodejs+npm-pkg:"tsx"'` |
| Anything more | write `.booth/setups/<name>--setup.sh` (runs as root at image build) with a `# cb-template: <Display name>` header, then `--add-select <name>` |
| More than one `setup` line (a package plus a script, run-args, a port) | write one file, `.booth/templates/<name>.toml` — `[segments]` plus the script inline under `[files.setups]`; no directory and no `meta.toml` — then `--add-select <name>` |

Never type a `setup` or `run` line into the Boothfile. A setup script named after a built-in
replaces that built-in, so choose a new name.

### After the change

A fresh `./booth` rebuilds the image from the new Boothfile, using Docker's layer cache. The
exception is a **kept-alive** booth resumed with `./booth start`: it keeps its old image. Have the
user `./booth remove` it, then run `./booth`.

## Drive an Existing Booth

When the toolchain lives in the booth, run the project's commands **through** it rather than on the
host:

```bash
./booth -- just test                    # one-shot booth: start, run, remove
./booth exec -- just test               # in the booth that is already running
./booth exec --run -- just test         # start it first if needed
./booth shell                           # an interactive shell in the running booth
```

`just --list` (inside, or via `./booth -- just --list`) shows the project's own recipes. Use them
rather than inventing commands.
A project with no Justfile can get one from `./booth just-init`. Its `{{run-in-booth}}` recipes
start the booth themselves, so `just test` works from the host as well.

Ground rules:

- **Look before you start anything long-lived:** `./booth list` shows every booth, its port and the
  code path it was started from.
- **Never stop or remove a booth you did not start.** It may be the user's working session.
- **Clean up the booths you did start** (`./booth stop <name>`, `./booth remove <name>`) when your
  check is done. Leave running anything the user asked you to start for them.
- A second booth from the same folder is named `<project>-<port>`. Pass that name to `exec`,
  `stop` and `remove` to target it.

Useful while debugging: `./booth logs` (`--startup`, `lifecycle`), `./booth --dryrun --verbose`
(the `docker run` it would execute), `./booth expose list` (published ports and tunnels).

## What NOT to Do

| Don't | Do instead |
|---|---|
| Write or edit `.booth/Boothfile` / `config.toml` | `booth config` with flags; `--add-select` for additions |
| Restate `--select` with part of the list | `--add-select` / `--remove-select` |
| Mount credentials with hand-written `-v` run-args | The credential templates |
| Hand-write a `.booth/Dockerfile` for a new booth | `booth config` — Dockerfile booths lose the TUI and the catalog |
| Run `booth config` with the project path as an argument | `cd` into the project first |
| Add `dind` / privileged options without saying why | Explain the host-access trade-off first |
| `docker stop` / `docker rm` a booth | `./booth stop` / `./booth remove`, and only booths you started |
| Install the toolchain on the host to get unstuck | Run it through the booth, or tell the user what is blocking |

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `docker: permission denied` | User not in the `docker` group (`sudo usermod -aG docker $USER`, log out/in) |
| "cannot run on Linux rootless Docker" | Unsupported; use rootful Docker or Docker Desktop |
| `booth config` refuses: hand-written file | Someone edited it in a way config cannot read back. Show the user `--beside` (writes `.new` to merge) vs `--overwrite` (keeps theirs as `.bak`); let them choose |
| Port already in use | `--port NEXT`, or stop what holds it (if it is not the user's) |
| Booth refuses to start: `cache/` not gitignored, or an env file would be committed | Add the reported path to `.booth/.gitignore` |
| A tool is missing after a change | A resumed keep-alive container — `./booth remove`, then `./booth` |

---

## Handoff: Going Inside

Once the booth is running and work continues inside it, this guide no longer applies. An agent
inside the booth reads `/opt/codingbooth/AGENT.md`. There is no `booth` CLI in there, and `.booth/`
is read-only.
