# TODO — Prove the catalog works

An audit of how much of the setup catalog is *proven to work* versus merely proven to be
*present*. The standard: a test for a setup should make the tool do the thing a user would do
with it in the first five minutes. Installing a compiler and only running `gcc --version`
proves a file landed on the PATH, not that it can compile.

Generated by reading `variants/base/setups/`, `templates/`, and every runtime test under
`tests/complex/`. Counts are as of version 0.66.0--rc1.

## Method, and what it cannot see

A setup counts as having a **runtime test** when some test's `.booth/Boothfile` names it, so a
real image is built and a real booth runs. Each such test was then classified by the strongest
assertion it makes, by reading the commands it hands to the booth:

- **Functional** — the tool is made to do work: compile and run a program, execute a script,
  serve and answer a request, run a query.
- **Presence** — `--version`, `command -v`, `dpkg -s`, `--help`, `list`. Proves installation,
  not function.

Classification was done by reading, not by pattern-matching: a first pass with regexes
mislabelled `duckdb --version` as functional because the word `duckdb` appears in a
database-client pattern. Treat the category counts as sound and any individual line as worth
a second look.

Not covered by this audit: the 194 `*--extension.toml` files, VS Code extension setups (they
have their own registration checks in `test-boothfile-code-extension`), and notebook kernels
beyond `bash-nb-kernel`.

## Worth fixing first

**Languages that install a compiler or runtime nobody ever runs.** This is the case that
started the audit. Each already has a test and a booth image — the gap is one compile-and-run
assertion, modelled on `test-boothfile-gcc`:

> `crystal`, `dotnet`, `elixir`, `elm`, `go`, `haskell`, `jdk`, `julia`, `lua`, `nim`, `php`,
> `rescript`, `roc`, `ruby`, `rust`, `swift`

**Languages with no runtime test at all** — these need the fixture too, not just the assertion:

> `clojure`, `erlang`, `fpc`, `kotlin`, `octave`, `r-rscript`, `scala`, `zig`

**Databases and servers, where "it starts" is the whole promise.** None of the seven is
exercised: start it, connect, write a row, read it back. `nginx` and `apache` are the same
shape — serve a file and `curl` it. `test-nginx-expose` already proves the plumbing, so the
pattern exists to copy.

> presence-only: `kafka`, `mongodb`, `rabbitmq`, `redis` · untested: `mysql`, `postgresql`, `sqlite`

**Tools whose subcommands are the product.** `terraform`, `helm`, `kubectl`, `ansible`,
`conda`, `gradle`, `sbt` stop at `--version` or `help`. A plan/render/dry-run against a tiny
fixture would prove far more and still needs no network.

## What cannot be fully proven, and why that is fine

Best effort is the standard. Some of the catalog cannot be exercised in a build:

- **AI CLIs** (`claude-code`, `codex`, `aider`, `gemini-cli`, `grok`, `opencode`, …) need an
  account and a paid API call. `--help` is close to the ceiling; where a credential *is*
  seeded, that it lands in the right path and is readable can still be checked — see
  `test-claude-code-credential-cache`, which does exactly that.
- **Desktops, browsers, IDEs, education tools** (`eclipse`, `bluej`, `greenfoot`, `scratch`,
  `drracket`, `gimp`, `freeplane`) are GUI applications; launching one headless proves little
  and costs a lot of build time.
- **Cloud CLIs** (`aws-cli`, `gcloud`, `azure-cli`, `firebase`) would need real projects and
  credentials. A local `--dry-run`/`validate` against a fixture is the honest ceiling.

Where the ceiling is low, say so in the test rather than dressing a presence check up as
proof.
